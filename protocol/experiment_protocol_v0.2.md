# Experiment Protocol v0.2

## 1. Research Objective

Investigate cross-LLM generalization of behavioral detection
for indirect prompt injection (IPI) in LLM agents.

The experiment trains independent behavioral detectors using
execution trajectories generated by different source LLMs and
evaluates detector transfer across LLMs.

The primary behavioral target is `ipi_affected`, which indicates
whether observable agent behavior was affected by the injected
attacker instruction.

The presence of an injection (`condition = ipi`) is not by itself
considered evidence that the agent was behaviorally affected.

## 3. Source LLMs

The initial API-based model plan from Experimental Protocol v0.1
was replaced because the project does not have an API budget.

The post-pilot candidate source LLM set is:

- LLM-A: gemma4:12b
- LLM-B: qwen3.5:9b
- LLM-C: lfm2.5

All three models are executed locally through Ollama.

The same selected scenarios, benign controls, injected payloads,
tools, permissions, and workflow must be used for all three models.

Exact Ollama model digests must be preserved in the execution
metadata.

### Model-selection note

LLM-C was selected after local model qualification testing because
the originally considered llama3.1:8b frequently emitted intended
tool calls as plain text rather than executable tool calls.

The LLM-C selection used performance observations from the same
nine benign pilot user tasks. Therefore, the nine pilot scenario
groups are treated as development / qualification scenarios and
must not be treated as an unseen final test set.

This does not prevent gemma4:12b, qwen3.5:9b, and lfm2.5 from being
used as the three source LLMs in the full experiment.

## 4. Local Inference Environment

Inference runtime:
- Ollama version: 0.35.0

Hardware:
- GPU: NVIDIA GeForce RTX 3060
- GPU memory: 12 GB
- CPU: Intel Core i7-11700K
- RAM: approximately 32 GB

Pilot context length:
- 16384 tokens for all three models

Pilot agent limits:
- max_steps = 15
- timeout = 180 seconds per execution
- retry <= 4 attempts

A fresh AgentDojo environment is required for every execution.

All retry attempts must remain recorded.
A successful retry must not silently replace evidence from
previous failed attempts.

---

## 5. Generation Settings

For Pilot v0.1:

- Temperature was not explicitly configured.
- Random seed was not explicitly configured.
- Thinking mode was not explicitly disabled.
- Hidden reasoning was not collected.
- Only observable model messages, tool calls, tool results,
  and environment effects were logged.

Therefore, exact output-level reproducibility is not assumed for
the first pilot.

Before the full experiment, generation settings and thinking-mode
policy must be explicitly frozen and recorded for every source LLM.

Any change to generation settings after Pilot v0.1 must be
documented as a protocol revision rather than silently applied
retroactively to the existing pilot.

---

## 6. Attack Configuration

Attack method:
- Fixed-template indirect prompt injection

Attack payloads:
- Use the fixed payloads stored in
  output/pilot_payloads.json for the pilot scenarios.

Do not generate a model-specific attack payload.

For the same scenario group, each source LLM must receive the same
payload and injection vector.

Record the payload SHA-256 for every IPI execution.

Do not adapt the attack based on the behavior or output of an
individual source LLM during the controlled experiment.

---

## 7. Benign Control

For each selected scenario group, execute the same legitimate user
task without the attacker payload.

The benign execution must:

- Start from a fresh copy of the same initial environment
- Use the same tools and permissions
- Use the same agent workflow
- Use the same maximum-step and timeout policies
- Preserve the original benign content at the selected injection
  location

Benign and IPI executions must remain paired by scenario group.

---

## 8. Controlled Conditions

The following experimental conditions should be held equivalent
across source LLMs wherever technically possible:

- User task
- Initial environment state
- Injection location
- Injection vector
- Fixed attacker payload
- Available tools
- Tool permissions
- Agent workflow
- Maximum agent steps
- Execution timeout
- Context limit
- Ground-truth criteria
- Logging schema
- Hardware
- Local inference runtime

Differences inherent to model architecture, tokenizer, model size,
and model-specific tool-calling behavior must be recorded rather
than hidden.

---

## 9. Pilot Execution

Pilot v0.1 consisted of:

- 9 scenario groups
- 2 conditions per group: benign and IPI
- 3 source LLMs
- 1 repetition
- 54 planned executions
- 54 completed executions

No execution ended with a system timeout or unrecovered execution
error.

The pilot is used for:

- Pipeline validation
- Local LLM qualification
- Logging validation
- Ground-truth refinement
- Leakage-policy refinement
- Estimation of task utility, injection exposure, and attack
  behavior
- Planning the full experiment

The pilot sample size is not sufficient for final claims about
detector performance or cross-model generalization.

The nine pilot scenario groups must not be used as the final
unseen held-out test set because they were already used during
model qualification and protocol refinement.

---

## 10. Execution Isolation

Reset the AgentDojo environment before every execution.

No run may inherit environment state from another run.

Only AgentDojo's simulated services and tools may be used.

Attack scenarios must not interact with real banking systems,
real email accounts, real calendars, or real attacker endpoints.

---

## 11. Required Logging

Every execution must have a globally unique `run_id`.

Required execution metadata includes:

- run_id
- scenario_group_id
- scenario ID
- suite
- user_task_id
- injection_task_id when applicable
- condition
- repetition identifier
- source LLM
- exact model identifier
- Ollama model digest
- AgentDojo version
- AgentDojo commit
- context length
- maximum steps
- timeout policy
- retry information
- execution status

Required observable trajectory information includes:

- Ordered agent messages
- Actual LLM-generated tool calls
- Tool names
- Tool arguments
- Tool results
- Tool errors
- Step order
- Environment-changing actions
- Final observable model output

For IPI runs, logging must also support determination of:

- ipi_present
- injection_inserted
- injection_encountered

Synthetic benchmark ground-truth actions must never be recorded as
if they were actions generated by the source LLM.

Hidden chain-of-thought or private reasoning must not be collected.

---

## 12. Ground Truth and Labels

Ground-truth annotation follows
`ground_truth_protocol_v0.2.md`.

The following concepts must remain separate:

- ipi_present
- injection_inserted
- injection_encountered
- ipi_affected
- benchmark_security
- strict_attack_succeeded
- benchmark_utility
- adjudicated_user_task_succeeded
- execution_status

`condition = ipi` must not be treated as the final behavioral
positive label.

The primary detector target is `ipi_affected`.

A benchmark security success does not automatically imply strict
attacker-objective success.

A failed strict attack may still have `ipi_affected = 1` if the
agent exhibits observable attacker-directed behavior.

An injection that was not encountered by the model must not be
interpreted as evidence of successful resistance.

---

## 13. Feature Separation and Leakage Control

Detector features must be derived from observable execution
behavior rather than ground-truth or attack metadata.

The following are prohibited as primary detector features:

- condition
- injection_task_id
- injection metadata
- injection payload
- injection payload hash
- selected injection vector
- scenario IDs that reveal condition
- source_llm
- model_id
- provider
- run_id
- benchmark utility/security outcomes
- adjudicated labels
- evaluator notes
- pre/post evaluation answers
- runner-generated injection-delivery events
- raw textual tool results
- raw assistant message content
- final-output text
- raw textual values of tool arguments

Model identity may be used to partition source-model datasets and
construct the cross-model evaluation matrix, but not as an input
feature in the primary detector.

Primary behavioral features should focus on model-agnostic
structural behavior such as:

- Number of agent steps
- Number of tool calls
- Number of unique tools
- Normalized tool categories
- Tool-call order
- Action transitions
- Sequence repetitions
- Loops / repeated behavior
- Tool errors
- Structural argument metadata such as argument count and type

Timing, latency, token counts, and infrastructure-dependent
measurements are excluded from the primary feature set unless
separately justified.

---

## 14. Dataset Splitting

Pilot v0.1 is treated as development / qualification data.

The full experiment must use group-based splitting.

The grouping key must preserve all variants and repetitions of the
same user task within the same split.

At minimum, grouping must include:

- suite
- user_task_id

Benign and IPI variants of the same task must remain together.

The same split assignment must be used for all three source LLMs.

Attack templates and closely related attacker goals must also be
checked to prevent leakage across train and held-out test sets.

The final held-out test set must not be used for:

- Model qualification
- Feature selection
- Hyperparameter tuning
- Detector selection
- Threshold tuning

---

## 15. Cross-Model Evaluation

One detector is trained for each source LLM using the same
detector algorithm and training procedure.

For three source LLMs, evaluate a 3 x 3 train-to-test matrix:

- Detector A -> LLM-A, LLM-B, LLM-C
- Detector B -> LLM-A, LLM-B, LLM-C
- Detector C -> LLM-A, LLM-B, LLM-C

Primary evaluation metrics should include:

- Precision
- Recall
- F1-score
- Confusion matrix

The cross-model generalization gap must compare same-model
performance against cross-model performance using a predefined
metric such as F1-score.

Pilot detector results must be reported only as pipeline-validation
results and not as final estimates of generalization performance.

---

## 16. Repetitions and Re-Execution

The first pilot contains one repetition per model, condition, and
scenario group.

The same pilot scenarios may be re-executed after protocol
freezing as an additional repetition for stability analysis.

A new repetition must:

- Receive a new run_id
- Preserve the original Pilot v0.1 run
- Record its repetition identifier
- Preserve the frozen model/runtime/settings metadata

A new repetition must not overwrite the first pilot.

If generation settings, thinking policy, model digest, parser
behavior, or other major experimental settings change, the new
execution must be documented as a distinct protocol condition and
must not be treated as an identical repetition.
